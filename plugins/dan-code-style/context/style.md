# Code conventions

Conventions for the code Claude writes. Design defaults, held loosely — any
of them yields when the problem at hand genuinely disagrees.

One principle unifies them: **make the structure of the code coincide with the
best explanation of the system — and let nothing vary that the explanation
doesn't account for.** Reify what the explanation mentions (give it a name and
a syntactic home); forbid what it doesn't (no degree of freedom without a
name). When a case below doesn't cover something, decide from the principle.

## Naming
- **Names should be mechanically derivable from the concept.** A reader who knows the concept in your head should arrive at the same name you wrote, without consulting a translation table. Three consequences:
  - **Spell words out fully — everywhere, with no "it's just internal" exception.** Prefer `index` over `i` or `idx`, `repository` over `repo`, `configuration` over `config`, `documentation` over `docs`, `decomposition` over `decomp`, `properties` over `props`, `sample-organization` over `sample-org`. This applies to **every** identifier equally — public APIs, private/internal items, struct/type/enum names, function names, and local variable names. Don't abbreviate a concept even in a private struct or a throwaway local: `SuitDecomposition` not `SuitDecomp`, `let decomposition` not `let decomp`. "Nobody else sees it" / "it's just a variable" is never a reason to abbreviate — the whole point is that the name reads the same everywhere. Genuine exceptions, narrowly: keep canonical ecosystem names as-is (the `config/` directory, `package.json`'s `config` field); established shared-vocabulary short forms (`id`, `url`, `api`, `json`, `http`) are fine; and a single-letter counter in a tight loop body is fine. The test: if the short form is an abbreviation of a *concept*, spell it out; if it's shared vocabulary or a trivial loop counter, leave it.
  - **Use the same name for the same concept everywhere.** If a type is `GameSessionStore`, the attribute is `gameSessionStore`, the parameter is `gameSessionStore`, the variable is `gameSessionStore`. Don't rephrase mid-stream — every rename is a translation tax on the reader.
  - **Be strict about singular vs. plural.** The same concept doesn't appear as `user` in one place and `users` in another. Pick the form that matches what the symbol refers to (one vs. many) and stay with it.
- **Don't stutter.** When an identifier is already namespaced — by module, class, struct, enum, or directory — don't repeat that namespace in the inner name. Prefer `strategic::SCORE_VERSION` over `strategic::STRATEGIC_SCORE_VERSION`; `StrategicBot::Score` over `StrategicBot::StrategicScore`; `io::Error` over `io::IoError`; `tile/category.ts` exporting `TileCategory` (not `tile/tile_category.ts` re-exporting from `tile/category.ts`). The namespace already provides the qualifier — repeating it makes call sites verbose and signals nothing the path doesn't already say.
- **Filename mechanically follows the primary identifier.** When a file defines a class, interface, or top-level construct, the filename is that identifier in the language's canonical file-case (snake_case in Python and Ruby, PascalCase in C# and Java, kebab-case in TypeScript when that's idiomatic). `PresidioAnalyzer` lives in `presidio_analyzer.py`, not `presidio.py`, and its test file follows (`presidio_analyzer_test.py`). Don't abbreviate or thematize away the obvious name (`archiving.py` for a `class ArchivingSource`). When a file would naturally hold more than one top-level construct, either split it so each gets its own filename, or name the file after the primary one (supporting types travel with it); a file that is a grab-bag of peer units is named for their shared theme instead. Avoid generic fallback names like `base.py`, `types.py`, `utils.py`, `helpers.py` — they hide content and force a reader to open the file to discover what's in it. The filename should answer "what does this define?" without being opened.

## Default to the standard form
- **Build things the most normal way, in the field's own terms of art.** Before inventing a structure or a name, ask what this problem is called in its domain and how the canonical treatment shapes it — then use that shape and that vocabulary unless a real constraint forbids it. Standard forms compound: they let training-data knowledge bear directly on the code, they make the next question easier to ask precisely, and they teach the reader the state of the art as a side effect.
- **No jank.** A workaround that routes around the design instead of modeling the problem is a signal to stop and re-derive the principled approach, not to ship the workaround with a comment. When the principled form comes into view mid-build, refactor toward it rather than accreting around the old shape.
- **Name the deviation.** Where the standard form genuinely doesn't fit, say so where the deviation lives — what the standard way is and which constraint rules it out — so the departure reads as a decision rather than ignorance.

## Code structure
Design defaults, held loosely — any of them yields when the problem at hand genuinely disagrees.
- **Lead with the highest-level abstraction.** Whether in a file, a function body, a module, or a directory, the reader encounters the top-level abstraction first and descends into details only when they need them. Top-level APIs come before helpers; high-level steps in a function come before the subroutines they call; module-level constructs come before file-level helpers. Newspaper style — headline first, article second.
- **Decompose at a single level of abstraction.** Write small functions whose sub-components operate at one consistent level. Use intention-revealing sub-functions to achieve this even when a sub-function is called only once — the structure and naming should make the body read as a short sequence of steps at one level, each delegating to a lower level that handles the details. Prefer this decomposition over comments; code structure should be self-documenting.
- **Split by comprehension load, not line count.** A file, function, or line is too big when a reader must hold too many things at once to follow it — not when it crosses a size threshold.
- **Keep functions small, splitting on control-flow complexity.** Long conditional chains and accumulating nesting are comprehension load in branching form — each path is one more thing the reader holds. The split is generative, not just reductive: each extraction forces a name, minting an abstraction one tier down — the layer that one-altitude reading then organizes.
- **Be strict on nesting: zero levels is the ideal, two is the tolerance.** Deep indentation is the "V" antipattern. Flatten with the language's own vocabulary first — guard clauses/early returns, and higher-order collection operations (map/filter/group-and-apply) that dissolve iteration nesting rather than wrapping it. Ease the restriction when reaching zero would force wrapper functions that name nothing ("perform this thing over this group"), make other code uglier, or fight what's canonical in the framework at hand.
- **Write confident code.** A function should read linearly from top to bottom without forcing the reader to track unresolved branches in their head. Front-load uncertainty: preconditions, defaults, edge cases, and errors get handled at the top with guard clauses, early returns, or input coercion, and exit in place. Past the guards, the body operates with confidence that happy-path conditions hold — the reader never has to ask "am I in the error branch right now?" because by construction they aren't. This pairs naturally with many small functions at a single abstraction level: each one receives confident inputs from its caller's guards, so it never has to defensively re-check. Prefer early-return guards over nested if/else. Avoid letting error state ride through the rest of the function body as a thread the reader has to keep tracking. (Avdi Grimm's *Confident Ruby* is the canonical reference; the principle is language-agnostic.)
- **Pull implicit patterns out.** A pattern that lives as a scatter of calls across sites is invisible, unnameable, and untestable; extract it into a named interface.
- **Interfaces get first pick of the names.** The abstract interface takes the plainest domain name — the word an explanation of the system would use — and implementations take the qualified names (`PaymentGateway` the interface, `StripePaymentGateway` an implementation), so calling code reads as the domain story with no implementation vocabulary leaking up. The name itself is the canonical domain operation, never mechanics or data topology (`charge`, not `post_card_request`); shape-names are honest only for genuine I/O adapters.
- **Expose the smallest public surface that is still correct**, flexible only where flexibility is actually needed. Behind it, organize the file top-down: public functions first, then the tier-1 private functions they call, then tier-2, and so on down.
- **Inject dependencies through interfaces, and use classes functionally.** Instance variables are the injected collaborators, wired in the constructor so the main method is pure work over them. Anything else stateful must earn its place with a specific, named reason.
- **Wire production and end-to-end tests through one shared factory.** Its arguments are only the dependencies a test environment must swap; everything else is constructed inside, identically for both callers — the signature itself documents exactly where test and production may differ, and tests exercise the wiring that actually ships.
- **Encapsulation and testing discipline are force multipliers — raise them together, as a ratchet.** A small surface is a small contract (fewer tests cover more) and a seam is where a fixture can stand; in return, tests against the surface pin the contract so everything behind it can be reworked safely. Test-setup pain is the diagnostic: when a scenario is hard to construct, the missing thing is almost always a boundary, not more mocks.
- **The testing pyramid is a default, not a rule.** Deviate deliberately where the problem demands a particular test strategy, and shape end-to-end suites along how the app is actually used (its real user journeys).
- **Lean on the test environment, not dev.** To verify a behavior, build an isolated test scenario whose fixtures construct exactly the situation in question — a dev check proves the code ran once under whatever state dev was in, and the proof evaporates; a scenario proves it repeatably and joins the suite as a regression guard. Shared dev keeps only the final integration smoke against real external systems.

## Public interfaces
- **One canonical way per concept.** Prefer minimal public interfaces. Avoid exposing multiple variants of the same method (`choose` and `choose_with_metadata`) as parallel public API — pick the richest signature as the canonical one; callers who need less use the subset. Internal performance optimizations (skipping expensive fields in hot paths, recording, logging, caching) are implementation details, not API shape; don't let them fork method signatures.
- **Don't re-export from package init files.** Callers import from the canonical module path where the symbol is actually defined. Keep `__init__.py` (Python), `index.ts` (TypeScript when used as a barrel), `mod.rs` (Rust) empty or minimal rather than restating `from .x import Y; __all__ = ["Y"]`. Imports earn their length by documenting where things live; "go to definition" works trivially; refactoring a symbol's location doesn't leave stale re-export breadcrumbs. The exception is a published library that needs a stable public API surface independent of internal layout — but for internal or application code, always prefer canonical paths.

## Code style
- **Spaced-out, "scientific style" formatting.** Lean toward more whitespace: blank lines between logical steps, and a willingness to break a construct onto an indented new line rather than packing it tight. The general rule: **a multi-line block is surrounded by blank lines on both sides** — one before its first line and one after its last — because a block needs room to breathe to be visually processed as a block rather than as lines bleeding into their neighbors. So a single-line sibling sitting immediately above a multi-line entry gets separated from it too; only *consecutive single-line* entries pack together with no blank lines. The exception is the containing block's own opening: the first child hugs its parent (no blank line after `def foo():`, a `mapping:` key, or an opening `(`/`{`/`[`), and nothing is inserted before the container's closing token. A comment introducing a block belongs to that block, so the blank line goes above the comment, never between the comment and what it introduces.
- **Don't add box/banner comment dividers** (e.g. a line of `#` or `-`/`=` repeated as a section rule) to new code. If a file already has them, leave existing ones alone rather than stripping them mid-task, but don't introduce the pattern in files you write.
- **Format code for diff stability — never by alignment.** No hanging alignment (continuation lines aligned under an opening paren or an earlier token) and no vertical column alignment across neighboring lines (padded column names/types in DDL, aligned trailing comments): a one-token edit then rewrites the whole block in the diff. A continuation line is indented one step past its parent line, nothing more. A comment that would trail in an aligned column goes on its own line above instead. Applies everywhere code lives in git, SQL/DDL and config included; a code block in a rendered design document may align for readability, since nothing diffs it.
- **YAML: block style by default; flow style only for an entry that fits on one line.** A `{…}`/`[…]` earns its compactness only when the whole entry fits within the file's line width (~100 unless the project sets tighter). The moment it would wrap, write the entry in block style — one key per line, one indent step — and never wrap *inside* a flow construct, which is the worst of both styles. In a block sequence the spaced-out rule applies: a multi-line entry gets a blank line after it before the next `-`; consecutive one-line entries pack. Comments sit on their own line above the entry they describe, never trailing — a trailing comment is what pushes the line past the limit, and a column of them is alignment.

## Comments and documentation
- **Describe current state, not history.** Documentation, code comments, and docstrings describe what the system *is* and *does* now. Don't narrate how it got there or defend the current design against rejected alternatives. Avoid framings like "we used to do X but switched to Y," "this was previously unsafe but is now safe," "bundling these enforces the invariant that the broken state is unrepresentable" (which implicitly contrasts with the rejected design), or "this reads as informative rather than redundant" (defending against an objection no current reader has). Once a decision is made, the structure reflects it; the previous state lives in git history. If the rationale matters, put it in a decisions doc framed forward (principles → consequences), not as a backwards-looking footnote in unrelated docs.
- **Comments explain *why* or *how*, not *what*.** The code already says what. Good comments capture intent, constraint, or non-obvious subtlety that the function name and signature can't carry. Test: "Does this tell me something I couldn't see from the function name and signature?" If no, delete it.
- Don't annotate code or docs with the historical path that led there — previous steps, intermediate forms, "we used to do X." Once the right form is found, prior scaffolding belongs in commit history, not in the file. The file should reflect what is, not what was. Watch for the subtler version of this: a negative/contrastive reassurance ("you won't hit X," "no waiting period," "unlike before") that only makes sense against a process the reader never experienced. It doesn't say "we used to," so it won't pattern-match against that phrase — but it's the same failure mode. If a claim's only content is the absence of something the reader has no baseline expectation of, cut it.

## Tooling and formatting
- **Use the canonical formatter, keep it enforced, and never reformat in passing.** Prefer the language's standard formatter (rustfmt, prettier, black, gofmt) over hand-formatting, and wire its `--check` into CI so formatting can't drift. A formatter is all-or-nothing for a codebase: either it's clean (run it freely, even on save) or it has drifted. **Before running a formatter on an unfamiliar codebase, check whether it's already clean** (`fmt --check`); if it reports diffs against committed code, the code has drifted and you must not reformat in passing — a drive-by reformat churns dozens of files, buries your actual change, and conflicts with every in-flight branch. On drift there are exactly two honest moves: (1) **adopt** it deliberately — one isolated reformat commit with zero logic changes, wire `--check` into CI, and add that commit's SHA to `.git-blame-ignore-revs` so blame skips it; or (2) **leave it** and hand-match the surrounding style for your change only. Never perpetuate a drifted style as a permanent stance, and never silently reformat code you happened to touch.
- **Composition over inheritance.** When multiple types share behavior, extract the shared logic into a module of free functions they can import, not a base class they extend.
- **Dependencies are required, not defaulted.** Constructor parameters for dependencies should be required, not optional with defaults. Optional parameters are appropriate when the default is intrinsic to the object (e.g. `id` defaulting to a generated UUID), but never when the default exists to hide a knob from callers or to spare you from updating call sites. The wiring should be visible at the call site. No clever defaults that make things "just work" if you forgot to specify a dependency.
- **Single source of truth (with judgment).** A given piece of knowledge or computation should have one implementation; the failure to avoid is *re-implementing* something the codebase already does, which surfaces as two functions computing the same thing that then drift. Before writing a non-trivial operation, pause and ask whether it already exists — first from what you've already seen of the codebase (the cheapest check, and often the answer is already in front of you), then a *targeted* search only if it's plausibly-existing and you're genuinely unsure. This is a moment of reflection before re-implementing an operation, **not** a mandate to grep before every line — reaching for the lowest-level primitive (e.g. a shared scorer) is not the same as checking whether the whole *operation* already exists. Two calibrated exceptions, named when taken: (1) **experimental or short-lived code** — if a shared abstraction would impose real bookkeeping or coupling to support code that may not survive, a local, clearly-flagged duplication is the right call; don't buy an abstraction whose shape you don't yet trust. (2) **incidental duplication** — code that looks alike but encodes *different* concepts that merely coincide today; keep it separate, because merging creates false coupling that breaks the moment one concept diverges. DRY is one source of truth for one piece of *knowledge*, not deduplication of textual similarity.

## Data and persistence
- **Persist raw inputs, derive features offline.** When recording data for later analysis or training, store the raw *state* needed to recompute any derived feature — not just the features you happen to want today. Recording only derived outputs (a computed score, a progress metric, an embedding) throws away the inputs, so every *new* feature forces you to regenerate the entire dataset by re-running the expensive producer. The test for a row: *"could I compute a brand-new feature from this alone, without re-running the producer?"* If not, you're persisting conclusions, not inputs. Record the full state even when today you only consume a scalar derived from it (e.g. store the complete hand — concealed tiles *and* melds — not just the four progress numbers you currently read off it). Derived columns are fine as a convenience/cache, but they must be *redundant* — reproducible from the raw columns in the same row — never the only copy.

## Relational databases (greenfield only)
- **Database tables are named as the plural of the entity each row holds** (e.g. `members`, `coverage_spans`, `field_value_candidates` — not `field_value_candidate`). A table name reads as "a collection of <entity>".
- **A table's primary key is `id`** — never `<entity>_id`, which stutters against the table name (`decisions.id`, not `decisions.decision_id`). A *foreign* key is `<referenced_entity_singular>_id` (`decision_id`), so a join reads `on d.id = c.decision_id` rather than sharing one column name across both sides.
- **Every table carries `created_at`**, defaulted to system time. It is an audit column and **never load-bearing** — no query filters or joins on it for logic, and no business rule reads it. Semantic clocks are their own named columns (`decided_at`, `first_seen`, `effective_date`); don't let `created_at` stand in for one, and don't reach for it as a point-in-time axis.
- **Database name pattern**: `<project>_<environment>` — `my_app_development`, `my_app_staging`, `my_app_production`. Predictable across projects.
- When working with an existing database, follow its existing conventions even if they differ from the above.
- **Database object names are spelled out too** — databases, schemas, tables, and columns included: `OPERATIONS`, not `OPS`.

## Avoiding things that rot
General principle: prefer artifacts that stay correct on their own over ones that must be maintained by hand to stay true. If keeping something accurate means updating it every time the underlying thing changes, it will drift — so don't create it, or derive it from the source.
- Don't write content that mirrors live state and will need updating every time that state changes — folder listings, file inventories, "current" enumerations of things that grow. Prefer describing the pattern or access method, not the current contents. Let a directory tree be its own index rather than maintaining a list of what's in it.
- Don't annotate code or docs with the historical path that led there — previous steps, intermediate forms, "we used to do X." Once the right form is found, prior scaffolding belongs in commit history, not in the file. The file should reflect what is, not what was. Watch for the subtler version of this: a negative/contrastive reassurance ("you won't hit X," "no waiting period," "unlike before") that only makes sense against a process the reader never experienced. It doesn't say "we used to," so it won't pattern-match against that phrase — but it's the same failure mode. If a claim's only content is the absence of something the reader has no baseline expectation of, cut it.
- Comments should explain *why*, not restate *what* the code does. A comment that narrates the code duplicates it and rots the moment the code changes; prefer intention-revealing names and small functions so the code documents itself, and reserve comments for rationale, constraints, and non-obvious context the code can't express.
- Avoid shotgun surgery: prefer changes that stay local to one place over ones that force the same edit in many. Keep a single source of truth; if one conceptual change would ripple across many files (parallel lists, duplicated constants, dense cross-references), that's a signal to restructure so the change lives in one spot.
- Code and config describe the system *now* — never cite a design-doc filename, directory path, or the dev-history from a comment, docstring, or name (`(see foo.md § X)`, "renamed from", "Sprint B will fill this"). Such a pointer rots the moment the doc moves or the history recedes, and it turns a doc rename into shotgun surgery across code. State the *why* in place; let docs be discovered, not hardcoded into code.

## Published artifacts
- **The source file is the deliverable; the published page is a rendering of it.** So the source lives where its subject already lives — the repo's `docs/`, the notes tree — and **never in a session scratchpad**. Temporary directories get cleaned out, and once that happens the published URL is the only copy: it can no longer be updated from a later session, and nothing survives the artifact being deleted.
- **Publish when the deliverable has an audience** — a design note, a walkthrough, a review someone else is meant to read. Analysis that answers a question in the conversation stays in the conversation, and a working file stays a file; a page nobody was going to open is just a second place for the same content to rot.
- **One artifact, one source path.** Republishing that path updates in place and holds the URL; publishing from a new path mints a second URL and silently orphans the first. Keep the artifact's URL recorded with its source, so a later session passes it back rather than minting a duplicate.

## Documents and PR descriptions
- **Code blocks inside markdown documents wrap at 64 columns, hard.** Rendered viewers (Slack, narrow panes) soft-wrap longer lines mid-word and wreck the layout, and 72 still wraps in practice. When a trailing comment would push a line past 64, shorten it or move it to its own line above; split wide statements (`create index`, long `check (...)`) across lines. After writing or editing a fenced block, verify no line exceeds 64 before calling it done.
- **A PR description is a living artifact while the PR is open, and the same rule binds it.** Don't enumerate the branch's commits (the Commits tab is the live index; per-commit detail belongs in the commit messages themselves) and don't quote counts that CI or the checks tab reports live (test totals, asset counts, "N tests pass"). Describe the branch's *shape* and what *gates* the merge, and let the checks render the status. A number belongs in a PR body only as an explicitly dated, won't-be-re-measured measurement (e.g. "verified against one prod snapshot on <date>: N rows"), never as a standing claim about the current state.

## Reviewing code
- When reviewing a diff, **treat every rule loaded into the session as its own pass over the changes** — section by section, across every instruction file in context, rather than whichever rules the diff happens to bring to mind. A violation is a finding even when the code is correct: these are the rules the code is held to, and a reviewer who knows them will raise it.
- **A convention violation is verified by quoting the rule and citing the line.** It needs no failure scenario — the rule is the standard, so correct-but-non-conforming code is still a finding. Quote the rule verbatim rather than paraphrasing it, so the claim can be checked against what the rule actually says.
- **A claimed defect does need a concrete failure** — specific inputs or state, and the wrong output or crash they produce. Check also whether it is **pre-existing in the base** rather than introduced by the diff, since a diff shows unchanged context lines too. A wrong defect claim costs more than a miss: it spends the author's attention and teaches them to skim.
- Diff against the **merge base** (`git diff <base>...HEAD`, three dots) so commits that landed on the base after the branch started don't read as the branch's own changes.
