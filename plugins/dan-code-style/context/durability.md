# Writing things that stay true

One of several files of conventions for the code Claude writes. Design
defaults, held loosely — any of them yields when the problem at hand genuinely
disagrees.

## Avoiding things that rot
General principle: prefer artifacts that stay correct on their own over ones that must be maintained by hand to stay true. If keeping something accurate means updating it every time the underlying thing changes, it will drift — so don't create it, or derive it from the source.
- Don't write content that mirrors live state and will need updating every time that state changes — folder listings, file inventories, "current" enumerations of things that grow. Prefer describing the pattern or access method, not the current contents. Let a directory tree be its own index rather than maintaining a list of what's in it.
- Don't annotate code or docs with the historical path that led there — previous steps, intermediate forms, "we used to do X." Once the right form is found, prior scaffolding belongs in commit history, not in the file. The file should reflect what is, not what was. Watch for the subtler version of this: a negative/contrastive reassurance ("you won't hit X," "no waiting period," "unlike before") that only makes sense against a process the reader never experienced. It doesn't say "we used to," so it won't pattern-match against that phrase — but it's the same failure mode. If a claim's only content is the absence of something the reader has no baseline expectation of, cut it.
- Comments should explain *why*, not restate *what* the code does. A comment that narrates the code duplicates it and rots the moment the code changes; prefer intention-revealing names and small functions so the code documents itself, and reserve comments for rationale, constraints, and non-obvious context the code can't express.
- Avoid shotgun surgery: prefer changes that stay local to one place over ones that force the same edit in many. Keep a single source of truth; if one conceptual change would ripple across many files (parallel lists, duplicated constants, dense cross-references), that's a signal to restructure so the change lives in one spot.
- Code and config describe the system *now* — never cite a design-doc filename, directory path, or the dev-history from a comment, docstring, or name (`(see foo.md § X)`, "renamed from", "Sprint B will fill this"). Such a pointer rots the moment the doc moves or the history recedes, and it turns a doc rename into shotgun surgery across code. State the *why* in place; let docs be discovered, not hardcoded into code.

## Published artifacts
- **The source file is the deliverable; the published page is a rendering of it.** So the source lives where its subject already lives — the repo's `docs/`, the notes tree — and **never in a session scratchpad**. Temporary directories get cleaned out, and once that happens the published URL is the only copy: it can no longer be updated from a later session, and nothing survives the artifact being deleted.
- **Publish when the deliverable has an audience** — a design note, a walkthrough, a review someone else is meant to read. Analysis that answers a question in the conversation stays in the conversation, and a working file stays a file; a page nobody was going to open is just a second place for the same content to rot.
- **One artifact, one source path.** Republishing that path updates in place and holds the URL; publishing from a new path mints a second URL and silently orphans the first. Keep the artifact's URL recorded with its source, so a later session passes it back rather than minting a duplicate.

## Documents and PR descriptions
- **Code blocks inside markdown documents wrap at 64 columns, hard.** Rendered viewers (Slack, narrow panes) soft-wrap longer lines mid-word and wreck the layout, and 72 still wraps in practice. When a trailing comment would push a line past 64, shorten it or move it to its own line above; split wide statements (`create index`, long `check (...)`) across lines. After writing or editing a fenced block, verify no line exceeds 64 before calling it done.
- **A PR description is a living artifact while the PR is open, and the same rule binds it.** Don't enumerate the branch's commits (the Commits tab is the live index; per-commit detail belongs in the commit messages themselves) and don't quote counts that CI or the checks tab reports live (test totals, asset counts, "N tests pass"). Describe the branch's *shape* and what *gates* the merge, and let the checks render the status. A number belongs in a PR body only as an explicitly dated, won't-be-re-measured measurement (e.g. "verified against one prod snapshot on <date>: N rows"), never as a standing claim about the current state.
- **A doc marked self-contained carries no cross-references at all** (the marking means it is meant to be shared): inline whatever it needs so it stands alone.

## Reviewing code
- When reviewing a diff, **treat every rule loaded into the session as its own pass over the changes** — section by section, across every instruction file in context, rather than whichever rules the diff happens to bring to mind. A violation is a finding even when the code is correct: these are the rules the code is held to, and a reviewer who knows them will raise it.
- **A convention violation is verified by quoting the rule and citing the line.** It needs no failure scenario — the rule is the standard, so correct-but-non-conforming code is still a finding. Quote the rule verbatim rather than paraphrasing it, so the claim can be checked against what the rule actually says.
- **A claimed defect does need a concrete failure** — specific inputs or state, and the wrong output or crash they produce. Check also whether it is **pre-existing in the base** rather than introduced by the diff, since a diff shows unchanged context lines too. A wrong defect claim costs more than a miss: it spends the author's attention and teaches them to skim.
- Diff against the **merge base** (`git diff <base>...HEAD`, three dots) so commits that landed on the base after the branch started don't read as the branch's own changes.
